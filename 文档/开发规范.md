# 取色卡 开发规范

> **本文定位**：高频编码规范的唯一真源——写代码、审查代码时必读。
> **专项规范**：领域细节已拆分至 `文档/专项规范/`，按需阅读。

## 1. 概述

### 1.1 项目简介

取色卡（Color Card）是一个基于 PySide6 开发的图片颜色分析工具，用于从图片中提取颜色信息和分析明度分布，支持多种色彩模式显示。

**核心功能：**

- 图片导入（JPG、PNG、BMP、GIF）
- 色彩分析：可拖动取色点，实时显示色彩值
- 多色彩模式：HSB、LAB、HSL、CMYK、RGB
- 明度分析与直方图可视化
- 双面板数据同步

### 1.2 开发环境

- **操作系统**：Windows 10/11
- **Python 版本**：3.11+
- **GUI 框架**：PySide6 + PySide6-Fluent-Widgets
- **推荐 IDE**：VS Code、PyCharm、Trae

### 1.3 项目结构

```text
color_card/
├── main.py              # 程序入口
├── version.py           # 版本管理模块（版本号唯一真源）
├── core/                # 核心功能模块（业务层，含服务层，多数为 *_service.py）
├── ui/                  # UI模块目录（扁平化结构，展示层）
├── dialogs/             # 对话框模块目录
```

## 2. 代码组织规范

### 2.1 文件命名规范

- 采用小写字母和下划线命名，如 `color_utils.py`
- 核心功能模块使用清晰的描述性名称
- 合并后的模块使用复数形式命名，如 `cards.py`、`histograms.py`、`canvases.py`

### 2.2 模块划分

|  模块类型 |     职责    |                 示例文件                 |
| :---: | :-------: | :----------------------------------: |
|  入口模块 |   应用程序入口  |               `main.py`              |
|  核心模块 | 颜色、图片、配置、预览、更新等服务（详见 §3.3.1） |   `core/color.py`, `core/config.py`  |
| UI 模块 |  界面组件和面板  |    `ui/canvases.py`, `ui/cards.py`   |
| 对话框模块 |   弹出对话框   |       `dialogs/about_dialog.py`      |
|  工具模块 |    通用功能   | `utils/icon.py`, `utils/platform.py` |

### 2.3 目录结构原则

**扁平化结构（2级目录）：**

```text
color_card/           ← 第1级
├── core/            ← 第2级
├── ui/              ← 第2级
├── dialogs/         ← 第2级
└── utils/           ← 第2级
```

**设计原则：**

- 主程序模块目录（core / ui / dialogs / utils）不超过 2 级，避免过度嵌套
- 将紧密相关的类合并到同一文件，减少文件数量，提高内聚性
- 保持功能模块化，职责明确

**核心理念：UI层和业务层分层，公共模块统一管理，业务模块按需调用；UI层只负责UI，功能层面全部下到业务层**

### 2.4 资源路径规范

**约束：资源路径不得依赖代码文件自身的位置。** 源码运行与打包后（PyInstaller / Nuitka）的目录结构不同，用 `__file__` 推算项目根目录会在打包后失效。

- 项目根路径只保留一个解析入口：所有模块统一调用 `get_base_path()`（实现位于 `utils/icon.py`），禁止自行推算或复制解析逻辑。`main.py` 因启动顺序早于工具模块可用，保留本地实现，是唯一例外。
- 新增资源目录或数据文件时，必须同步更新 `build-windows.yml` 的两处 Nuitka 调用（便携版、安装版）与 `build-mac.yml`；漏改会导致对应平台打包后资源缺失。

### 2.5 导入规范

**导入顺序：** 标准库 → 第三方库 → 项目模块

```python
# 标准库导入
import sys
from pathlib import Path

# 第三方库导入
from PySide6.QtWidgets import QApplication
from qfluentwidgets import FluentWindow

# 项目模块导入
from core import get_color_info
from ui import MainWindow
```

**规范要求：** 按模块类型分组导入，定期清理未使用的导入，合并同一模块的多次导入，统一使用绝对导入。

## 3. 代码编写规范

### 3.1 基本规范

- 遵循 **PEP 8** 代码风格规范
- 使用 4 个空格缩进
- 保持代码简洁，删除无用的调试代码和临时测试代码

### 3.2 核心原则

以下六条是所有编码决策与审查的基准。**作用域**：只约束本次变更新增或触碰的代码；存量违规标注「已知存量」，报告末尾带过，不要求本次修复（重构单独提交）。

- **存量加重例外**：存量缺陷因本次改动后果加重（数据丢失、失败路径新增、终端用户可见结果改变）时，不按存量带过，须入正文并按后果定级，修不修由开发者裁决。
- **冲突裁决**：原则相斥时按序——任务越界（§3.2.3）> 不加抽象（§3.2.1）> 拆分（§3.2.4）。
- **豁免沉淀**：审查中反复出现的误报写入各条「不算……」清单，与原则一并维护。
- **工具兜底**：本次实际运行且通过的工具，其覆盖的信号不重复核对；工具未运行或不在覆盖范围内时仍须人工核对，覆盖边界见 §8.10。
- **跨处常量单一真源**：同一概念多处硬编码时指定一处为真源，其余位置注释指回。本项目已登记：`version.py`、`utils/theme_colors.py`、`scenes_data/` 与预览代码的契约字段；版本号的同步要求见 §5.3。

#### 3.2.1 避免过度设计

不为「可能会用到」写抽象。典型：只调用一次的独立文件 / 接口 / 工具函数、为稳定结果加缓存层、在已有状态方案外再包一层。

**自检动作**：为每个新增抽象说出复用处；仅一处调用且无复用价值即移除。

**不算过度设计**：`_update_styles()` 主题刷新模式、`core/*_service.py` 服务层、`utils/theme_colors.py` 颜色 getter、`dialogs/base_frameless_dialog.py` 基类。

#### 3.2.2 避免冗余代码

未使用的代码立即删除，不留「备用」。典型：未使用的导入、声明后未调用的函数与变量、声明后从未读取的参数、注释掉的整块代码。

**自检动作**：列出本次新增的导出符号，逐一确认有消费方；新增或修改测试时确认 mock 字段与辅助函数形参有消费方。

**不算冗余代码**：Qt 事件重写方法（`paintEvent`、`mousePressEvent` 等，由事件分发机制调用）、跨模块经 `self._service` 动态调用的方法（已登记在 `pyproject.toml` 的 vulture 白名单）。

#### 3.2.3 避免无效修改

改动不产生实际效果，或超出任务范围。**技术无效**：如同一目标两条冲突样式规则、改了参数但调用方传的是另一个参数。**任务越界**：改动非本次任务范围的文件；格式化变更与功能变更混杂提交；发现范围外问题应在回复中报告而非顺手修，确需顺带修复的须在交付说明中指出位置。

**自检动作**：对照变更集逐处判断归属——属于本任务或豁免范围，写不出理由的即越界，交付前移除。

#### 3.2.4 避免复杂逻辑

阈值：函数 50 行、嵌套 3 层、同类条件分支 5 个、行长 100 字符；行数口径为声明到结束，不含空行与纯注释行。超过即拆分或说明为何不可拆。正则须注释说明意图，魔法数字须提取为命名常量（语义自明的基数除外）。

**自检动作**：为新增函数报告行数与分支数；超阈值说不出豁免理由的按违规处理。

#### 3.2.5 避免过度防御

不对「理论上不可能发生」的场景防御。典型：对框架保证存在的对象做存在性检查、对类型系统已保证的值重复收窄、对底层已兜底的错误再兜底、多层可合并的异常捕获。

**不算过度防御**：终端用户输入校验、文件与网络 IO 失败处理、调用顺序无法调整时的 `hasattr` 守卫、对 `requirements.txt` 中必需依赖不写防御导入与回退。

**自检动作**：为每个空值检查 / 类型收窄 / 错误兜底说出触发的真实输入；说不出的交付前移除。

#### 3.2.6 命名清晰

名称表达意图，风格与项目既有命名一致。典型：函数名超过 4 个词、名称带实现细节、布尔变量缺语义前缀（作用域已自明时豁免）、同一概念在同一文件内混用不同名称、随意缩写。颜色空间分量按下文 §3.3.2 的大写简写命名。

**自检动作**：为每个新增名称说出一句领域释义（哪个域、什么概念）；说不出的改从既有命名惯例复用。

### 3.4 异常处理规范

**基本原则：** 禁止使用裸 `except:` 或 `except Exception:`，必须指定具体异常类型，并提供详细的错误信息。

```python
# 错误示例
except Exception:
    pass

# 正确示例
except (OSError, ValueError) as e:
    error_msg = f"文件读取失败: {str(e)}"
```

**基本原则：** 所有公共类和方法必须添加文档字符串；使用简洁的中文描述，避免冗余；类文档字符串保持简洁（单行或简短段落）；方法文档字符串包含 Args 说明，有返回值时补充 Returns。

```python
class ImageCanvas(QWidget):

def set_image(self, image_path):
    """加载并显示图片

def get_color_info(self, r, g, b):
    """获取颜色信息
    
    Args:
        r, g, b: RGB通道值 (0-255)
    
    Returns:
        dict: 包含RGB、HSB、LAB、HEX颜色信息的字典
    """
```

### 3.7 类型注解规范

**基本原则：** 项目要求 Python 3.11+，使用 PEP 585 内置泛型语法；避免使用 `typing` 模块中已弃用的类型（如 `typing.List`、`typing.Dict` 等）；公共方法应添加返回类型注解。

**类型对照表：**

| typing 旧类型（避免） |    内置泛型（推荐）    | 说明   |
| :----------: | :--------------: | :--- |
| `List[元素类型]` | `list[元素类型]`     | 列表类型 |
| `Dict[键类型, 值类型]` | `dict[键类型, 值类型]` | 字典类型 |
| `Tuple[元素类型, ...]` | `tuple[元素类型, ...]` | 元组类型 |
| `Optional[T]` |   `T \| None`    | 可选类型 |
|  `Type[类名]`  | `type[类名]`       | 类型对象 |

```python
from typing import Any

def get_colors(self) -> list[str]:
    return ['#FF5733', '#33FF57']

def get_config(self) -> dict[str, Any]:
    return {'name': 'test', 'value': 123}

def find_item(self, item_id: str) -> dict[str, Any] | None:
    return None
```

### 3.7.1 Nuitka 打包兼容性要求

**核心原则：使用 PEP 585 内置泛型（如 `list[int]`、`dict[str, Any]`）的文件，必须在顶部添加 `from __future__ import annotations`。**

**判断是否需要添加：**

| 使用的类型注解 | 是否需要 |
| :---: | :---: |
| 仅简单类型（`str`、`int`、`bool`、`float`、`None`） | ❌ |
| PEP 585 泛型（`list[...]`、`dict[...]`、`set[...]`、`tuple[...]`） | ✅ 必须 |

`from __future__ import annotations` 必须放在文件最顶部（文档字符串之后，所有导入之前）。

### 3.8 主题与样式规范

主题切换、`_update_styles()`、颜色函数与 Qt 原生功能禁用见《专项规范/界面与主题规范》§5、§6、§13、§14。

### 3.9 注释规范

- 注释解释代码本身：为什么这样写、约束是什么，不复述代码在做什么。
- 不引用方案文档及其章节 / 阶段（不写「见《X方案》阶段一」「按方案第 3 步」）——方案会移动、阶段会作废，引用必然悬空；把方案里的结论直接写成结论本身。
- 不引用规范章节号；需要指路时指向代码或配置的真源（具体文件与符号名）。
- 判据：注释单独摘出来、不查任何文档也能读懂。

## 6. 重构规范

### 6.1 重构原则

1. **保持功能不变**：重构过程中不改变现有功能
2. **渐进式重构**：分阶段进行，每阶段可独立验证
3. **先整理后重构**：先规范现有代码，再提取基类，最后重组目录
4. **代码清理同步**：修改代码时同步清理相关重复代码

### 6.2 基类提取规范

步骤：分析相似组件的公共逻辑 → 设计抽象方法接口 → 迁移第一个子类验证设计 → 迁移其余子类 → 全量测试。各基类的职责、文件位置与必须实现的方法见《专项规范/基类设计规范》。

### 6.3 模块合并规范

**合并原则：** 将紧密相关的类合并到同一文件；避免过度拆分，提高代码可维护性；保持模块化，但减少文件数量。

**示例：** `cards.py` 合并 ColorCard、LuminanceCard 及相关基类；`histograms.py` 合并直方图组件及基类；`canvases.py` 合并画布组件及基类。

## 8. 测试规范

### 8.1 测试目录结构

```text
color_card/
├── tests/                      # 测试目录
│   ├── __init__.py            # 测试模块初始化
│   ├── test_*.py              # 测试文件
│   └── requirements-dev.txt   # 开发依赖
├── pytest.ini                  # pytest 配置文件
└── ...
```

### 8.2 测试框架配置

测试配置统一放在 `pytest.ini`，不得散落在测试代码或命令行参数里：`qt_api = pyside6`，marker 至少包含 slow / unit / integration / ui。

### 8.3 开发依赖

测试依赖统一登记在 `tests/requirements-dev.txt`，安装用 `pip install -r tests/requirements-dev.txt`；不在测试代码里另装依赖或写版本约束。

### 8.4 测试命名规范

| 类型   | 命名规则        | 示例                           |
| ---- | ----------- | ---------------------------- |
| 测试文件 | `test_*.py` | `test_threading.py`          |
| 测试类  | `Test*`     | `TestHistogramCalculator`    |
| 测试方法 | `test_*`    | `test_cancel_does_not_block` |

### 8.5 测试分类标记

使用 pytest marker 标记测试类型：

```python
import pytest

@pytest.mark.unit
def test_color_conversion():
    pass

@pytest.mark.slow
def test_large_image_processing():
    pass
```

运行特定标记的测试：

```bash
python -m pytest -m unit        # 只运行单元测试
python -m pytest -m "not slow"  # 跳过慢速测试
```

### 8.6 Qt 测试规范

**使用 pytest-qt：** pytest-qt 提供了 `qtbot` fixture 用于 Qt 组件测试。

```python
def test_button_click(qtbot):
    button = QPushButton("Click me")
    qtbot.addWidget(button)
    qtbot.mouseClick(button, Qt.LeftButton)
```

**等待信号：** 使用 `qtbot.waitSignal` 等待异步信号。

```python
def test_async_calculation(qtbot):
    calculator = HistogramCalculator(image, "luminance")
    with qtbot.waitSignal(calculator.finished, timeout=5000) as blocker:
        calculator.start()
    assert len(blocker.args[0]) == 256
```

### 8.7 线程安全测试

```python
import time

def test_cancel_does_not_block(qtbot):
    """测试 cancel() 不阻塞调用线程"""
    calculator = HistogramCalculator(image, "luminance")
    calculator.start()

    start_time = time.time()
    calculator.cancel()
    elapsed = time.time() - start_time
    
    assert elapsed < 0.01  # cancel 应该在 10ms 内返回
    calculator.wait(1000)
```

### 8.8 运行测试

```bash
python -m pytest                              # 运行所有测试
python -m pytest tests/test_threading.py      # 运行特定文件
python -m pytest -x                           # 在第一个失败时停止
python -m pytest --cov=core --cov-report=html # 生成覆盖率报告
```

### 8.9 测试最佳实践

1. **测试独立性**：每个测试应该独立运行，不依赖其他测试
2. **测试可重复性**：相同输入应该产生相同结果
3. **测试命名清晰**：测试名称应描述测试内容
4. **使用 fixture 复用代码**：提取公共设置代码到 fixture
5. **Mock 外部依赖**：使用 `unittest.mock` 隔离外部依赖

### 8.10 提交前检查与工具覆盖

| 检查项 | 命令 | 覆盖边界 |
|---|---|---|
| 测试 | `python -m pytest` | 行为回归；纯样式 UI 改动不强制补测试 |
| 类型 | `mypy` | 宽松配置（`check_untyped_defs=False`），只查带注解的函数 |
| 风格 / 未使用导入 | `ruff check <变更文件>` | 只跑本次变更文件；项目未配置格式化工具，不做全量格式化 |
| 未使用符号 | `vulture core ui dialogs utils main.py --min-confidence 60` | 依赖 `pyproject.toml` 白名单；Qt 事件方法与 `self._service` 动态调用存在漏报 |

CI（`.github/workflows/build-*.yml`）只做打包，不跑上述检查；提交前须在本地执行。

工具报错位于本次变更文件 → 入审查报告；位于未变更文件 → 判断是否由本次变更引起，否则记「存量问题」。工具未运行、因环境无法启动或不在覆盖范围内时，不得当作通过：无法启动标注「工具 X 未生效（原因）」，未运行/超出覆盖标注「未经工具验证」。

### 8.11 变更收集命令

```powershell
[Console]::OutputEncoding = [Text.Encoding]::UTF8
git -c core.quotepath=false diff HEAD --no-color --output=.git-diff.txt
git -c core.quotepath=false ls-files --others --exclude-standard
```

- 已跟踪差异与未跟踪新文件清单必须同时获取，缺一不可（`git diff HEAD` 不含 untracked）。读取后删除 `.git-diff.txt`，由本次执行方负责。
- 用 `--output` 落盘，不用 `>` 重定向（PowerShell 会写成 UTF-16）；`--no-color` 去 ANSI 转义码；`core.quotepath=false` 防中文路径被转成八进制。
- 复用已有差异的前提：之后未产生新变更，且上下文中确有完整差异。

### 8.12 忽略规则

- 忽略规则只在仓库根 `.gitignore` 维护，不在子目录新建 `.gitignore`——嵌套忽略会让范围内的文件静默脱离版本控制视野（状态不显示、添加被拒）。
- 新产物把规则并入根忽略文件并注明生成方式；脚手架自带的局部忽略文件删除。
- 例外：工具自动生成、且父目录已整体被忽略的（如 `.venv/`、`.pytest_cache/` 内的忽略文件）。

## 9. AI 协作规范

本文用「开发者」指参与协作的人，「终端用户」指应用的使用者；不再单用「用户」。

### 9.1 定位

**AI 生成的代码等同于新人提交的 PR**：不因生成速度快而降低审查标准；合入前必须经过 code-review 流程（见 `skills/code-review`）。

**结论性质**：审查报告是辅助意见，🔴 是「合入前须解决」的建议判定；是否放行、是否解除由开发者裁决，AI 不自行判定已解决。

### 9.2 三类行为须随交付讲清

涉及以下三类改动的代码，必须在交付代码的同时讲清实际行为（执行顺序、分支走向、输入输出、验证依据与对应测试）；不接受「看起来能跑」，审查阶段补写不算：

1. **异步时序**：QThread / 信号槽 / QTimer 的触发顺序、取消与竞态——「信号什么时候发、谁先谁后、线程退出时会发生什么」
2. **边界与异常**：空图片、超界坐标、文件读写失败等边界输入的实际走向——「最坏输入进来，代码走到哪一步」
3. **核心算法**：颜色转换、直方图、Zone 分区、配色生成等算法的数学含义——「这个公式算出来是什么、为什么正确」

**三条禁令**（讲清写错的最高发形态）：

- **禁用随改动漂移的量化描述**：不写「验证 10 例」，改写测试文件路径 + 关键用例名。
- **禁用绝对化断言**：不写「不存在竞态」，改写实况，如「已知存在 X 窗口（存量，未消除）」。
- **禁用覆盖范围概括**：不写「各入口均不再触发」，逐项列清单。

**语言**：写给开发者，不读代码也能核查；技术标识符只用于标注位置，不充当解释。

**门禁**：未随附讲清 → 🔴，写明须重点核查的场景；讲清与代码不符或自相矛盾 → 🔴，写明不符处。解除权在开发者。

### 9.3 授权与边界

- **审查的触发权在开发者**：方案 / todo 里写「审查」不构成授权，执行到此类待办时停下请求触发词；修复后复核自动进入，无需再次触发。
- **「修复以上问题」的默认范围**：代码与过程性文档记账；本规范、专项规范、skills、AGENTS.md 的改动须先说明拟改内容与理由，经开发者授权后执行。
- **提交动作由开发者执行**：任何流程都不提交、不推送。
- **方案级决策由开发者拍板**：选型取舍、行为边界、数据语义；AI 不替开发者决定，也不自主发起方案重写。
- **提问模式**：进入后只查阅、诊断、给建议，不新建 / 编辑 / 删除任何文件，不执行写盘与版本控制写操作，直到开发者给出修改指令；进入与退出各告知一句。

### 9.4 变更复杂度分档

| 档位 | 判据 |
|---|---|
| **简单** | 无逻辑改动（纯样式数值、注释、删除、重命名、简单格式、仅增删配置键且默认值与行为不变、无行为变化的代码迁移），上下文已完整覆盖，且不新增抽象 |
| **标准** | 单个模块内新增局部逻辑（状态、条件、事件处理、局部计算），不跨模块、不涉及三类行为；**存疑时取本档** |
| **复杂** | 跨模块联动、跨环境同步（开发环境与打包环境、多处版本号、`docs/` 与 `website/public/` 双份文件、`scenes_data/` 契约）、涉及三类行为、抽象层重构、上下文不足以确信覆盖 |

- 文件数不是判据。新增 `ui/`、`dialogs/` 叶子组件（不引入新抽象、不跨模块）与仅新增测试文件，按标准档。
- **高风险域最低取标准档**：配置迁移与数据删除（收藏、配色导入导出）、版本发布与打包兼容、QThread 取消时序。
- **只升不降**：先按简单档判断，命中任一条即升级——跨处共用常量、跨模块联动、三类行为、高风险域；简单档中的「重命名」不适用于跨文件常量。
- 配置键仅新增且默认值与行为不变 → 简单档；涉及配置迁移、删除或默认行为改变 → 按高风险域取标准档。
- 简单档的格式检查为 `ruff check <变更文件>`。

### 9.5 修复后复核

开发者提出修复要求后自动进入，不重跑三视角：

1. 按 §9.7 完成自检；触及三类行为的修复随修复交付讲清。
2. 逐条核对原报告的 🔴 / 🟡，确认已修复或说明未修原因。
3. 重跑 §8.10 的提交前检查。
4. 修复新增抽象或新增文件、改动落到本次审查未覆盖的逻辑区 → 升级为完整审查流程，最多一次；重跑后再次触发升级即停止，交开发者决策。默认串行，需派子代理时先给成本提示并征得同意。
5. 只报未修复项与检查未通过项；全通过输出「复核通过，可提交」。

### 9.6 产出物要求

- 审查结论、测试结论必须锚定实际命令输出（pytest / mypy / ruff / vulture 的退出码与输出），禁止凭推断断言「已通过」。
- 涉及第三方库 API 签名或运行时行为时，读 `site-packages/` 实际源码或官方文档验证，禁止凭记忆断言。
- 工具未运行或不在 §8.10 覆盖范围内时的标注要求见 §8.10。
- 跨会话文档的接力规则见 `skills/proc-doc`。

### 9.7 AI 生成代码约定

- **生成后自检**：对照 §3.2 各条自检动作逐条自查，交付前修正；审查已报 🔴 后不再改代码，待开发者提出修复要求后进入复核。
- **自审最多两轮**：第二轮无新问题即停手；仍有同类轻微项交开发者校准。
- **预制代码先自检**：照方案片段实施前逐条核对，不符先反馈再实施，不直接照抄。
- **预期行为先锚定**：行为语义无明示验收标准且存在多种合理解读时，列出候选询问开发者，禁止静默选定。
- **抄入断言须复算**：从方案 / 核实记录逐字抄入的计数、版本号、行号、库 API 行为须独立复算并注明结果；与来源不符先停下说明。

### 9.8 治理元规则

改本规范、专项规范、skills、AGENTS.md 时：

1. **先读全再动笔**：读目标文件全文与相邻文件；重叠的改旧句，矛盾的先解冲突，不新增第二份说法。
2. **单一真源**：同一约束只写一次，其他位置只写「见某节」。
3. **只加有证据的规则**：只给真实发生过、工具又查不出的静默失效加护栏；优先改现有句子。
4. **跨边界内联**：子会话指令、跨会话交接等对方看不到别处的内容须内联原文并注明来源；没有来源标注的重复才算双写。
5. **规则不外移**：规则写在本规范内，代码与配置是遵守方；规范只登记实现位置（如 `get_base_path` 在 `utils/icon.py`）和约束（必须包含哪些、改哪里同步），不写成「以某代码文件为准」。
