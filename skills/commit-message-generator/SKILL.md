# Commit Message Generator

## 工作流程

根据对话上下文，以**修改复杂度**（而非文件数量）判断采用哪种策略：

0. **排除 Git 忽略的文件**：被 `.gitignore` 忽略的文件（如 `.qoder/`、`文档/过程性文档/`、`demos/`、`测试/`、`测试图片/`、`影调分析/`、`配色方案/`、`打包/`、`指令合集.txt` 等）不会被提交，即使对话中修改过，也**一律不纳入提交信息**。若本次改动全部属于被忽略文件，直接告知用户"改动均为 Git 忽略文件，无需提交"。不确定某文件是否被忽略时，用 `git check-ignore <路径>` 验证。
1. **简单修改**：对话上下文能清晰概括全部改动的内容和意图时，直接基于对话生成提交信息，无需检查 Git 工作区。
   - 例如：加注释、删除代码、重命名、简单格式调整、加几行配置等——即使涉及多个文件也属于简单修改。
2. **复杂修改或无法判断**：对话中改动涉及新逻辑、重构、新增功能/类/方法，或对话上下文不足以确信能完整概括时，按以下步骤获取变更内容：
   - **复用已有 diff**：若本轮对话中已执行过 `git diff HEAD` 及 untracked 文件列表获取（如代码审查阶段），且之后未产生新的修改，直接复用已获取的内容，跳过重新执行 git 命令。
   - 否则执行 `[Console]::OutputEncoding = [Text.Encoding]::UTF8; git -c core.quotepath=false diff HEAD --no-color --output=.git-diff.txt; git -c core.quotepath=false ls-files --others --exclude-standard`，一条命令同时获取：① 暂存+未暂存变更→项目根目录临时 txt（`--output` 绕过 PowerShell 管道避免行尾截断与编码损坏，**禁止用 `>` 重定向替代**——PowerShell 会写成 UTF-16；`--no-color` 去除 ANSI 转义码；`-c core.quotepath=false` 防止中文路径被转义成八进制序列，本项目存在大量中文目录与中文文件名）；② untracked 新文件列表（`git diff HEAD` **不含 untracked 文件**，新建的模块/对话框/测试/配置会被漏掉；输出量小，直接读终端输出。不用 `git status -s`——ls-files 更快且输出更干净）。
   - 使用 Read 工具读取 `.git-diff.txt` 获取已跟踪文件的变更；untracked 新文件中对话上下文不足以概括的，用 Read 读取全量内容。
   - 生成提交信息后，若本次新建了 `.git-diff.txt`，删除 `.git-diff.txt`（已在 `.gitignore` 中）。
   - 若 diff 为空**且**无 untracked 文件，直接告知用户"工作区无变更，无需提交"。

## 分支合并场景

当用户要把功能分支合并到主分支（或填写 PR / merge commit 信息）时，提交信息概括**整个分支相对目标分支的净变更**，输出格式与普通提交一致（标题与修改项分别用围栏代码块包裹）：：

1. **确认分支**：用 `git branch --show-current` 确认当前分支；目标分支（`main` / `Dev` 等）从用户话语中确认，不确定时询问。
2. **获取变更**：`git log --oneline --no-merges <目标分支>..<源分支>`（本分支独有提交，`--no-merges` 过滤"从目标分支合回来"的 merge 提交）+ `git diff <目标分支>...<源分支> --stat`（净变更文件清单，**三点语法**，自动排除双方共同祖先之后目标分支的新提交）。若对话上下文（方案文档、落地记录）已能概括净变更，可跳过或仅抽查核对。
3. **标题**：`[类型] 合并 <源分支>：<核心目的概括>`，类型按分支主要目的取（新功能/优化/修复等）。
4. **修改项**：按功能模块归纳净变更，一条一个模块，**不逐 commit 罗列**——分支提交常有十几条，逐条复述与 diff 重复且冗长；"代码对比原则"在此同样适用（中间过程被后续提交覆盖的改动只记最终结果）。可从 stat 中识别纯辅助改动（如测试补充、文档微调）作为末尾补充条目。

## 输出规则

**输出两个独立的围栏代码块**：标题和修改项内容分别用 ``` 围栏代码块包裹，禁止任何解释性文字、标签、类型列表或示例说明：

```
[类型] 标题
```

```
- 修改项1
- 修改项2
```

两个代码块之间用空行隔开，不要连在一块。不要省略"[]"。

### 标题规范
- 使用中文，**动词开头**（如"新增"、"修复"、"优化"、"重构"）
- 控制在 50 字以内，简洁概括本次修改的核心目的

### 修改项规范
- 每条以 `- ` 开头，描述一个具体改动
- 说明改了什么，而非怎么改的

## 类型参考（内部使用，不输出）

可根据实际内容灵活命名，无需严格对应：新功能、修复、优化、重构、文档、样式、内容调整等。

## 实际输出案例

```
[新功能] 新增影调分析直方图均值线显示开关
```

```
- 影调分析对话框新增"显示均值线"开关，默认开启
- 直方图均值线可随开关实时显隐，颜色走 theme_colors.py 适配深浅主题
- 新增 show_mean_line 配置项，经 core/config.py 持久化
- 同步更新 tests/test_update_service.py 的配置 mock
```

## 代码对比原则

**只对比最终结果与初始代码**，忽略中间过程：合并同类修改，过滤被覆盖的中间变更。

例：初始 `a+b` → 中间尝试 `a-b`、`a*b` → 最终 `a+b+c`，只记录"返回值增加参数 c"。
