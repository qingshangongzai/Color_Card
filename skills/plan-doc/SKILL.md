# 方案文档写作规范

方案文档存放在 `文档/过程性文档/`，是跨会话协作的唯一接力载体：一篇文档 = 一个问题域的完整方案；一个会话通常只完成其中一个阶段，下一个会话的 AI 只靠读这篇文档就能继续干活。因此文档必须**决策完备**（执行者无需再做任何决策），且更新时**只追加、不重写**（两个例外：顶部进度行每次覆写；用户明确要求推倒重写，见接力规则末尾）。

## 新建文档

文件名：`XX方案.md` / `XX计划.md` / `XX分析.md`，直接放在 `文档/过程性文档/` 根目录（现有命名参考：《色盲模拟功能优化计划.md》《延迟加载机制分析.md》）。整个目录已被 `.gitignore` 整体忽略（`文档/过程性文档/`），新建文档无需单独处理忽略规则。规范类、需入库的文档（如开发规范、专项规范）仍放 `文档/` 根目录，不归本 skill 管。

需求已明确、即将实施 → 直接写方案文档（本节）。需求刚出现、**暂不实现** → 先写思路文档（见下文「思路文档」节），实施前再升级为方案。

### 结构模板

```markdown
# 标题（与文件名一致）

> **进度**：未开始｜下一步：阶段一

## 背景 / 问题

现状事实，写具体：文件路径、行数、症状、数量（如"`core/image_service.py`
约 600 行，12 个公开方法"）。引用其他方案文档用《文件名.md》，只写文件名、
不带目录——文件名在 文档/过程性文档/ 内唯一，被引用文档归档移动后引用仍有效。

## 核心决策 / 技术选型

每个决策必须带理由。被否决的备选方案写明为什么否决——防止后续会话
重新发明。多个选型对比时用表格：

| 考虑点 | 决策 |
|--------|------|
| 为什么不用 X？ | 理由（具体到本项目的约束） |

## 目标与范围

**做：** 编号列表，可验证的结果。

**不做（明确排除，避免过度设计）：** 同样重要，逐条写排除理由。

## 阶段规划

### 阶段一：名称

**目标**：一句话。

**任务**：具体到函数签名 / 数据结构 / 文件路径 / 信号连接 / 消费方清单，
关键代码直接给出片段。

**验收标准**：可勾选的客观条件（pytest 通过、启动耗时、UI 零改动等）。

### 阶段二：……

## 注意事项 / 风险

已知边界情况、预期中的"看似异常"行为、与其他文档条款的关系。
```

### 写作要求

- 小改动可省略"阶段规划"，直接按"核心逻辑改动（core/utils）/ UI 改动（ui/dialogs）/ 测试"分节。
- 阶段划分以"一个会话能完成 + 可独立验收"为粒度；阶段间依赖只能单向向前。
- **不写工期、不写人员分工、不写进度百分比**。
- 技术细节的标准：下一个 AI 读完后不需要再翻代码做任何方案级决策，只需实现。
- **写方案的会话只产出文档，不开始实施**（实施由后续会话按阶段进行），除非用户明确要求当场实施。

## 思路文档（轻量，可选前置）

需求出现但**暂不实现**时，不写决策完备的方案，只记录已确认的方向和未决问题——既避免细节过早固化，也避免讨论成果丢失。

文件名：`XX思路.md`（如《WebDAV 配色云同步思路.md》），放在 `文档/过程性文档/` 根目录。

**结构（轻量，无阶段规划、无验收标准）：**

- 背景 / 问题：需求 + 现状约束，几句话即可
- 产品形态 / 核心思路：已确认的方向性结论（如"每套配色只存一个 JSON 文件，永不搬家"）
- 对现有代码的接入点：核对过的文件路径 + 行号，推荐表格
- 已知风险 / 边界
- **待敲定**：checkbox 清单，显式列出未决问题——这是日后制定方案的对齐输入
- 兼容性结论（如涉及）

顶部进度行固定为：`> **进度**：思路记录（YYYY-MM-DD），细节待补全，升级为正式方案前不作实施依据。`

**更新规则：** 思路文档是草稿性质，无阶段、无落地记录，不进入接力流程；内容可随讨论直接更新（不受方案文档"只追加"约束），但「待敲定」清单只增不删——已解决的项打勾保留，不删除，保留追问痕迹。

**升级为正式方案：**

制定方案的第一步是**需求对齐**，不是动笔：

1. 先读对应的思路文档，把「待敲定」逐条向用户追问；没有思路文档但需求模糊的，同样先问再写。
2. 追问原则：**能自己查代码 / 文档确认的不烦用户；需要用户拍板的绝不替用户决定**。方案级决策（选型取舍、行为边界、数据语义）必须用户确认；代码级实现细节自己定。
3. 全部问清后，另建 `XX方案.md`，结论落进「核心决策」（含被否决的备选及理由）；此后思路文档正文不再改动。
4. 思路文档顶部进度行改为 `> **进度**：✅ 已升级为《XX方案.md》（YYYY-MM-DD）`，后续随该方案一并归档。

## 跨会话更新（接力）规则

这是本 skill 的核心。接手实施某方案时：

0. 动手前先用两三句向用户复述"当前进度 + 本会话计划完成什么"，让用户有机会纠偏。
1. 先看顶部进度行定位，再**读全文**核实：找到第一个没有 ✅ 标记的阶段（若有 🔨 阶段则优先续接其落地记录中的断点；无阶段的小型方案则看文末落地记录），并快速核对该阶段的前提与当前代码是否仍一致。进度行只是索引，与正文冲突时以阶段标记和落地记录为准。
2. 前提已失效（涉及的文件被删/重构、依赖变更、需求变化）时，**停下向用户说明**，按第 8 条作废流程处理；禁止自行改写计划来"适配现状"。
3. 计划部分（背景 / 决策 / 目标 / 阶段任务 / 验收标准）一经写定视为**只读**。实现与计划有偏差时，**不改原文**，偏差写进落地记录。
4. 阶段完成后，先逐条核验该阶段的验收标准，再在阶段末尾**追加**落地记录：

   ```markdown
   **落地记录（YYYY-MM-DD）**：  ← 日期必须从系统时间获取，禁止凭记忆填写

   - 实际改动摘要：新增/修改的文件、验收标准逐条核验结果
     （pytest 通过数、mypy/ruff 结果等）
   - 与计划条款的偏差及原因（如"未按逐像素遍历实现——性能不达标，
     改为 NumPy 向量化"）
   - 行为差异的裁决结果（保留旧行为还是采纳新行为，逐例写明）
   - 遗留给下一阶段的事项
   ```

5. 状态标记打在阶段标题上：**开始实施某阶段时立即打 `🔨 进行中`**（而非中断时才补——即使会话意外中断，文档也留下"此阶段有人动过"的痕迹），验收通过后改为 `✅ 已完成`，未开始不打标记。**会话在阶段中途结束时同样必须追加落地记录**：写明已完成部分、未完成部分、断点位置与下一步入口——这是下一个会话唯一的续接依据。同一阶段跨多个会话时，每个会话各追加一条落地记录，按时间顺序排列，**不合并、不改写已有条目**。无阶段的小型方案：落地记录统一追加到文档末尾的"落地记录"节，进度只靠顶部进度行体现。
6. 每次更新文档（打/改状态标记、追加落地记录）时，**同步覆写顶部进度行**。进度行是全文唯一允许覆写的区域，只写当前状态，不留历史，格式：

   ```markdown
   > **进度**：阶段二 🔨 进行中（YYYY-MM-DD）｜断点/下一步：一句话｜详见该阶段落地记录
   ```

7. **禁止**：重排章节、重写已有段落（顶部进度行除外）、删除历史落地记录、把落地记录内容合并回计划正文。
8. 需求变更导致某阶段失效时：不删除，在其标题标注"❌ 已作废"并一句话说明原因，新方案作为新阶段追加在末尾。
9. 追加内容使文档明显超出原问题域时，**另起新文档**并在原文档末尾一句话链接过去，不要让单篇无限膨胀。
10. 方案全部完成或决定暂停时，把顶部进度行改为`✅ 全部完成`或`⏸ 暂停（止于阶段X，原因一句话）`，再把文档移入 `文档/过程性文档/已实现-部分实现（暂停实现）/`（目录不存在则创建）。因引用一律不带目录，移动后无需修复其他文档里的引用；按文件名在 `文档/过程性文档/` 内递归搜索即可定位。

**例外——用户要求推倒重写**：用户对方案不满意、明确要求重写或重新开始时，上述规则全部让位：整篇按"新建文档"重写，旧内容（含历史落地记录、状态标记、❌ 作废条目）彻底删除，不保留任何痕迹。重写后的文档视为全新方案，**禁止出现"原方案""此前决定""改为"之类指向旧版本的表述**——旧版本已被抹掉，后续读者无从知晓它存在过。此例外仅限用户明确要求；AI 不得自主发起重写。
