# 过程性文档写作

`文档/过程性文档/` 存放五类跨会话文档，整体已被 `.gitignore` 忽略，不进版本库；AI 仍须可读，这是跨会话接力的唯一依据。规范类文档（开发规范、专项规范）放 `文档/` 与 `文档/专项规范/`，不归本 skill 管。

## 0. 先选类型

按**需求状态**选类型，不按文件名选：

| 诉求 | 类型 | 必备 | 归宿 / 可升级为 |
|---|---|---|---|
| 只记录现象，暂不调查 | 现象记录 | 现象 | → 分析记录 / 方案 / 归档 |
| 查清原因，只需结论 | 分析记录 | 现象 + 证据链 + 根因 | → 方案 / 归档 |
| 需求刚出现，暂不实现 | 思路文档 | 方向 + 待敲定 | → 方案 |
| 一个范围的批量问题 | 审查报告 | 范围 + 概述 + 问题清单 | → 方案（整改）/ 归档 |
| 需求明确，即将实施 | 方案文档 | 决策 + 验收 | → 归档 |

- **类型判定**：按诉求动词——「记录下来」→ 现象记录；「查为什么」→ 分析记录；「怎么改」→ 方案文档；「出报告」→ 审查报告；需求刚出现 → 思路文档。诉求有两种读法时先回问；开发者指明类型时按指明的写。
- **证据充分不构成升级依据**：升级须开发者确认。
- **可见闸门**：分析记录、审查报告、方案文档落盘前，先用一句话复述「诉求 → 拟写类型」，确认后再写；现象记录、思路文档不设。
- **落盘前重结构自检**：文中出现影响评估、优化建议、逐条状态、阶段规划而当前类型并不要求 → 类型选重，或删掉越界要素。
- **文件命名**：目录内唯一（含子目录），能表达内容；引用只写文件名、不带目录，归档移动后引用仍有效。类型后缀仅为建议。
- 审查报告是人工 / 周期性发起的宽范围独立审查产物，不是每次代码审查的输出（后者只在对话内，不落盘）。

## 1. 方案文档

文件名建议 `XX方案.md` / `XX计划.md`，放 `文档/过程性文档/` 根目录。

### 结构模板

```markdown
# 标题（与文件名一致）

> **进度**：未开始（YYYY-MM-DD）｜断点/下一步：阶段一｜基线：提交号 + 工作区状态（未提交改动必须写明）

## 背景 / 问题

现状事实，写具体：文件路径、行数、症状、数量。引用其他方案用《文件名.md》，只写文件名、不带目录。

## 核心决策 / 技术选型

每个决策带理由；被否决的备选写明为什么否决，防止后续会话重新发明。

| 考虑点 | 决策 |
|--------|------|
| 为什么不用 X？ | 理由（具体到本项目的约束） |

## 目标与范围

**做：** 编号列表，可验证的结果。

**不做（明确排除）：** 逐条写排除理由。

## 阶段规划

### 阶段一：名称

**目标**：一句话。

**任务**：具体到函数签名 / 数据结构 / 文件路径 / 信号连接 / 消费方清单，关键代码给片段。

**验收标准**：可勾选的客观条件。

## 注意事项 / 风险
```

### 写作要求

- 阶段划分以「一个会话能完成 + 可独立验收」为粒度，阶段间依赖只能单向向前。
- 不写工期、不写人员分工、不写进度百分比。
- 技术细节的标准：下一个 AI 读完不需要再翻代码做任何方案级决策。
- **写方案的会话只产出文档，不开始实施**（除非开发者明确要求当场实施）。

### 更新规则

- **决策完备**：执行者无需再做任何决策。
- **只追加、不重写**；例外：顶部进度行每次覆写；事实写错经开发者同意后更正正文；开发者明确要求推倒重写。
- 小改动可省略「阶段规划」，按「核心逻辑改动（core/utils）/ UI 改动（ui/dialogs）/ 测试」分节。

## 2. 思路文档（轻量）

需求出现但**暂不实现**时使用，文件名建议 `XX思路.md`。

**结构**：背景 / 问题；产品形态 / 核心思路；对现有代码的接入点（核对过的文件路径 + 行号）；已知风险 / 边界；**待敲定**（checkbox 清单，这是日后制定方案的对齐输入）；兼容性结论（如涉及）。不写阶段规划与验收标准，正文建议 600～1000 字。

顶部进度行固定为：`> **进度**：思路记录（YYYY-MM-DD），细节待补全，升级为正式方案前不作实施依据。`

**更新规则**：草稿性质，不进入接力流程，可随讨论直接更新；「待敲定」按 §8 累积清单规则维护。

**升级为方案**：先读思路文档，把「待敲定」逐条向开发者追问（能自己查代码确认的不问，需要拍板的绝不替开发者决定）；问清后另建方案文档，结论落进「核心决策」；思路文档进度行改为 `> **进度**：✅ 已升级为《XX方案.md》（YYYY-MM-DD）`，正文不再改动，随方案一并归档。

## 3. 现象记录（轻量）

只记客观现象：看到什么、何时出现、在哪。不写根因、不写建议；先记下来，升级时再核实。文件名建议 `XX现象.md`。

## 4. 分析记录（轻量）

一条证据链 → 一个根因，写文件 / 行号与排除项；不写建议；结论性变更须留痕。文件名建议 `XX分析.md`。

## 5. 审查报告（轻量）

宽范围问题清单，必备「范围 + 概述 + 问题清单」；每条独立推进状态。报告不承担实施，整改另起方案。文件名建议 `XX审查报告.md`。

## 6. 跨会话接力

接手实施某方案时：

0. 动手前用两三句向开发者复述「当前进度 + 本会话计划完成什么」，让其有机会纠偏。
1. 先看顶部进度行定位，再**漂移检测**（见第 7 节）：核对代码自「基线」之后是否变过。未变动的事实直接采信正文的「已核实」标记，不重核。进度行只是索引，与正文冲突时以阶段标记和落地记录为准。
2. 前提与现状不符时**停下向开发者说明**：失效（文件被删 / 需求变化）→ 按第 8 条作废；事实写错 → 提议更正正文或重写，经开发者同意后方可动正文。禁止自行改写计划来「适配现状」。
3. 计划部分（背景 / 决策 / 目标 / 阶段任务 / 验收标准）一经写定视为**只读**；实现与计划有偏差时，偏差写进落地记录。
4. 阶段完成后先逐条核验验收标准，再在阶段末尾**追加**落地记录：

   ```markdown
   **落地记录（YYYY-MM-DD）**：  ← 日期从系统时间获取，禁止凭记忆

   - 实际改动摘要：新增/修改的文件、验收标准逐条核验结果
   - 与计划条款的偏差及原因
   - 行为差异的裁决结果（逐例写明）
   - 遗留给下一阶段的事项
   - 讲清落点（触及异步时序/边界与异常/核心算法时，讲清写在哪）
   - 已决策豁免（供审查输入；豁免只覆盖所列决策，不得外推）
   ```

5. 状态标记打在阶段标题上：开始实施立即打 `🔨 进行中`，验收通过改 `✅ 已完成`，未开始不打标记。**会话在阶段中途结束时同样必须追加落地记录**：写明已完成部分、未完成部分、断点位置与下一步入口。同一阶段跨会话时各追加一条，按时间顺序排列，不合并、不改写已有条目。无阶段的小型方案：落地记录追加到文末「落地记录」节。
6. 每次更新同步覆写顶部进度行（全文唯一允许覆写的区域）：当前状态、断点 / 下一步一句话、基线（版本控制提交号 + 工作区状态，**未提交的改动必须写明**）。格式：

   ```markdown
   > **进度**：阶段二 🔨 进行中（YYYY-MM-DD）｜断点/下一步：一句话｜基线：提交号 + 工作区状态
   ```

7. **禁止**：重排章节、重写已有段落（顶部进度行除外）、删除历史落地记录、把落地记录内容合并回计划正文；追加修订节按语义命名，确需编号时用「修订 N」。
8. 需求变更导致某阶段失效时：不删除，标题标注「❌ 已作废」并一句话说明原因，新方案作为新阶段追加在末尾。
9. 追加内容明显超出原问题域时另起新文档，原文档末尾一句话链接过去。
10. 全部完成或决定暂停时更新进度行，移入归档子目录（见第 9 节）。

**例外——开发者要求推倒重写**：上述规则全部让位：整篇重写，旧内容（含历史落地记录、作废条目）彻底删除；重写后视为全新方案，禁止出现「原方案」「此前决定」之类指向旧版本的表述。仅限开发者明确要求，AI 不得自主发起。

## 7. 核实与漂移检测

同一份文档并存两类内容，处置相反：

- **设计**（方向、结构、步骤、选哪个）——**先写**：没有真伪，靠评审与迭代收敛。
- **事实**（现状约束、文件 / 行号、依赖是否存在、第三方库实际行为、平台差异）——**先核实再写**：不凭记忆写进正文；一时核不了的先记进现象记录，查清后再写进分析 / 方案。

**对应处理：**

- **核实**（撰写侧，一次完成）：方案落盘前完成；关键事实与结论旁标 `已核实（日期 + 方式）` 或 `待核实（含确认方法）`，方式写明代码检索 / 单元环境实测 / 真实环境实测。设计决策没有真伪维度，不标。预制代码须区分「示例」与「定稿」：给不出定稿时列出候选取值与依据，不要给一个看起来像定稿的错误值。
- **漂移检测**（执行侧，每次续接一次）：比对基线（提交号 + 工作区状态）与当前代码，查已核实项依赖的代码是否变过。无漂移 → 直接采信；有漂移 → 只重核变更文件触及的事实，其余照旧；前提确已失效 → 按接力第 2 条停下说明。基线漏记未提交改动会误报无漂移，以实际工作区为准并补记基线。
- **漂移检测不是核实**：只做这一次检测，不做全文复核；据此新写的代码仍须按《开发规范》§9.7 做生成后自检。
- **落点**：方案 / 思路 / 分析在落盘前完成；审查报告贯穿逐条推进；现象记录在升级时核实。

## 8. 累积清单

跨次累积的清单（待敲定、待核实、问题状态等）统一遵循三条：

1. **只增不删**：条目一经提出即保留；已解决的改状态后仍保留。
2. **状态就地更新**：有进展时改状态列，不新增一行、不另起一节复述。
3. **追加到表末 + 标注来源**：新条目注明提出轮次。

推荐四列形态：`| # | 内容 | 提出 | 当前状态 |`。

## 9. 归档

根目录 = 未收口（仍在推进）；归档子目录 `已实现-部分实现（暂停实现）/` = 已收口（完成 / 暂停 / 问题关闭）。方案完成或暂停时移入归档；其余四类随关联方案移入，无关联方案的结案由开发者确认、AI 只提议。因引用只写文件名，移动后无需修复引用。
