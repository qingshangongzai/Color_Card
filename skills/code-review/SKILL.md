# Code Review

> 编码规则（颜色管理、异常处理、类型注解、Nuitka 兼容、测试约定等）以《文档/开发规范.md》为唯一真源，领域细则见《文档/专项规范/》；本 skill 只负责审查流程与产出格式，冲突时以规范为准。

只读审查：只分析问题、给出结论，**不修改业务代码**；除本流程要求的 `.git-diff.txt` 临时文件外不写盘，验证命令必须只读，用退出码与实际输出锚定「通过 / 失败」等事实性结论，不凭推断断言。

**结论性质**：审查报告是辅助意见，🔴 是「合入前须解决」的建议判定；是否放行、是否解除由开发者裁决，AI 不自行判定已解决。

**实证原则（对抗幻觉）**：审查涉及第三方 Python 包的 API 签名或运行时行为（如 `qfluentwidgets` 的 `FluentWindow` 方法签名、PySide6 的 Qt 事件分发/信号槽机制）时，读实际源码（`site-packages/` 下的 `qfluentwidgets`、`PySide6`）或官方文档验证，禁止凭记忆断言——第三方库版本差异大，记忆极易过时。框架内部行为无法从项目代码直接看出时，标注"据经验，未验证"或补一次源码确认。

**讲清门禁**：涉及异步时序 / 边界与异常 / 核心算法的改动，先核对交付时是否随附讲清、讲清与代码是否相符（判定与三条禁令见《开发规范》§9.2），缺失或不符直接报 🔴。

## 审查流程

0. **排除 Git 忽略的文件**：被 `.gitignore` 忽略的文件不属于审查范围，即使对话中修改过，也**一律不审查、不出现在结果中**（git 命令本身会排除；基于上下文审查时也须遵守）。若本次改动全部属于被忽略文件，直接告知「改动均为 Git 忽略文件，不在审查范围内」；不确定时用 `git check-ignore <路径>` 验证。
1. **按变更复杂度分档**（判据以《开发规范》§9.4 为准，此处不重复）：
   - **简单**：无逻辑改动、上下文已覆盖、不新增抽象 → 跳过步骤 2–6，**不执行变更收集类 git 命令**（步骤 0 的 `git check-ignore` 只读校验除外），直接基于上下文审查；重点看「规范合规」「无效修改」与跨文件一致性，存疑点直接 Read 核实；补跑 `ruff check <变更文件>`
   - **标准**：单模块内新增局部逻辑 → 执行步骤 2–6，按三视角串行
   - **复杂**：跨模块 / 跨环境 / 三类行为 / 抽象重构 / 上下文不足 → 完整流程；子代理默认不派，需派时先征得开发者同意
2. **收集变更**：按《开发规范》§8.11 获取已跟踪差异与未跟踪新文件，两条缺一不可；差异落 `.git-diff.txt`。开发者指定文件则直接读全量。
3. **读取差异**：Read `.git-diff.txt`，阅读变更区域前后各 20 行；报告行号按 `@@` 段头换算后回读源文件确认真实行号，不直接使用 diff 内相对位置。
4. **确定性工具先行**：按《开发规范》§8.10 跑本次涉及的命令（全部只读）。失败项按正式问题入报告；报错位于未变更文件时判断是否由本次变更引起，否则记存量；工具因环境问题无法启动时标注「工具 X 未生效（原因）」，不得当作全绿。工具全绿不等于无问题。
5. **三视角审查**：按 **A 简洁性 → B 正确性 → C 合规** 顺序，每轮只回答本视角的问题，不一轮混看（见「审查维度」）。
6. **清理临时文件**：删除 `.git-diff.txt`（生成方负责；上次中断残留先清理）。
7. 仅输出有问题项，全通过输出"✅ 未发现问题"

## 审查维度

> 🔴 必须修复 | 🟡 建议优化

**视角 A · 简洁性（维度 1–5）**

### 1. 过度设计 🔴
不必要的抽象层只有一个实现；引入未使用的依赖；为"以后可能用到"写代码或加参数；简单逻辑套复杂模式。

判定与「不算过度设计」清单以《开发规范》§3.2.1 为准，此处不重复。

### 2. 冗余代码 🔴
变量赋值未使用；导入未引用；重复代码；dead code；空的 `__init__`/`pass`；注释掉的整块代码。

工具未覆盖的信号按《开发规范》§3.2.2 的人工核对清单处理；Qt 事件方法、`self._service` 动态调用不算冗余（白名单见 `pyproject.toml`）。

### 3. 无效修改 🟡
不影响运行结果的改动；只声明无实现；改了非任务范围文件（除非是顺带修复的明确 bug）；格式与功能变更混杂，应拆分为独立提交。

### 4. 复杂逻辑 🟡
嵌套过深、函数过长、同类分支过多未用查表法、魔法数字未提取、晦涩正则无注释。

阈值（50 行 / 3 层 / 5 分支 / 100 字符）与计数口径见《开发规范》§3.2.4，此处不重复。

### 5. 过度防御 🟡
对框架保证的属性做防御性检查、对不可能为 None 的值做 None 检查、多层可合并的异常捕获、`__init__` 中守卫 `setup_ui` 后才有的属性。

「正当防御」清单以《开发规范》§3.2.5 为准。

**视角 B · 正确性（维度 6）**

### 6. 正确性 🔴

三类行为（异步时序 / 边界与异常 / 核心算法）按《开发规范》§9.2 的讲清门禁判定：交付时未随附讲清，或讲清与代码不符、自相矛盾 → 🔴（判法见上文「讲清门禁」）。

此外核对**接口契约**：

- 版本号是否多处同步：`version.py`、`version.txt`，以及 `installer/`、`docs/`、`website/public/` 的 changelog
- `scenes_data/` 的配置字段与预览代码读取是否一致
- 跨模块共享结构改动，消费方是否同步修改

契约判断读两边实际代码，不凭调用链推断。

**视角 C · 合规（维度 7–8）**

### 7. 项目规范合规 🔴

仅检查**本次变更代码**，规则出处见下表（真源为《开发规范》与《专项规范/》）：

| # | 检查项 | 出处 | 违规信号 |
|---|--------|------|---------|
| 1 | 颜色管理 | 《专项规范/界面与主题规范》§6 | 硬编码颜色值（`QColor(r,g,b)`、`"#xxx"` 样式），需走 `theme_colors.py` |
| 2 | 异常处理 | 《开发规范》§3.4 | 裸 `except:` 或 `except Exception:`，需指定具体类型 |
| 3 | 日志输出 | 《专项规范/日志系统规范》§7 | 业务代码用 `print()`，需改用 `get_logger()` |
| 4 | 类型注解 | 《开发规范》§3.7 | `typing.List/Dict/Tuple/Optional`，需改 PEP 585 内置泛型 |
| 5 | Nuitka 兼容 | 《开发规范》§3.7.1 | 用了 `list[...]`/`dict[...]` 但无 `from __future__ import annotations` |
| 6 | 资源路径 | 《开发规范》§2.4 | 用 `__file__` 拼资源路径，打包失效，需用 `get_base_path()` |
| 7 | 线程安全 | 《专项规范/图片处理规范》§3 | `QThread.wait()` 阻塞 UI，需用标志位取消 |
| 8 | 主题适配 | 《开发规范》§3.8、《界面与主题规范》§5 | 需要随主题变化的组件缺 `_update_styles()` + `qconfig.themeChangedFinished` 连接 |
| 9 | 跨面板同步 | 《开发规范》§4.3、《界面与主题规范》§9 | `set_image_data` 等方法缺 `emit_sync` 参数防信号循环 |
| 10 | 注释合规 | 《开发规范》§3.9 | 注释引用方案 / 阶段 / 文档编号，或复述代码在做什么 |

> 仅简单类型的文件不需要第 5 项检查。

### 8. 测试完整性 🔴

项目用 pytest + pytest-qt，测试位于 `tests/test_*.py`。审查逻辑层（`core/`、`utils/`）改动时检查：

- 改动了 `core/` 服务或 `utils/` 工具函数的行为，但对应 `tests/test_*.py` 未同步更新，导致测试失败或与实现脱节
- 修改了被测函数的签名或返回值，却未更新断言
- 新增有明确输入输出的纯函数（颜色转换、算法类逻辑），完全无测试覆盖
- 测试中 mock 的模块路径与实际导入路径不一致

> 纯 UI 组件（`ui/`、`dialogs/`）、纯样式改动不强制补测试。

## 修复后复核

审查报出问题、开发者提出修复要求后自动进入，按《开发规范》§9.5 执行，不重跑三视角：完成自检 → 逐条核对原报告 🔴/🟡 → 重跑提交前检查 → 判断是否升级（最多一次）→ 只报未修复项与未通过项。

## 输出格式

| # | 文件:行号 | 严重度 | 维度 | 问题描述 |
|---|----------|--------|------|---------|
| 1 | xxx.py:65 | 🔴 | 冗余代码 | 变量 `result` 赋值后未使用 |
| 2 | xxx.py:120 | 🟡 | 复杂逻辑 | 函数 `parse_data` 超 50 行 |
| 3 | xxx.py:45 | 🔴 | 项目规范合规 | 硬编码颜色，应使用 `get_text_color()`（《界面与主题规范》§6） |

- 每项附 1-2 句修复建议
- 🔴 必须修复项排在前面，🟡 建议优化项排在后面
- 与本次变更无关的存量问题不入正文，末尾一句带过（存量加重例外见《开发规范》§3.2 总则）
- 若某维度无问题，不输出该维度
