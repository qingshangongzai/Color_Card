# Code Review

> 编码规则（颜色管理、异常处理、类型注解、Nuitka 兼容、测试约定等）以《文档/开发规范.md》为唯一真源，领域细则见《文档/专项规范/》；本 skill 只负责审查流程与产出格式，冲突时以规范为准。

只读模式：只分析问题、给出结论，**不修改任何代码**。但允许（且建议）运行只读的验证命令——`python -m pytest`、`mypy`、`ruff check` 等——用退出码与实际输出锚定"通过 / 失败 / 格式问题"等事实性结论，不要凭推断断言。

**实证原则（对抗幻觉）**：审查涉及第三方 Python 包的 API 签名或运行时行为（如 `qfluentwidgets` 的 `FluentWindow` 方法签名、PySide6 的 Qt 事件分发/信号槽机制）时，读实际源码（`site-packages/` 下的 `qfluentwidgets`、`PySide6`）或官方文档验证，禁止凭记忆断言——第三方库版本差异大，记忆极易过时。框架内部行为无法从项目代码直接看出时，标注"据经验，未验证"或补一次源码确认。

## 审查流程

0. **排除 Git 忽略的文件**：被 `.gitignore` 忽略的文件（如 `.qoder/`、`文档/过程性文档/`、`demos/`、`测试/`、`测试图片/`、`影调分析/`、`配色方案/`、`打包/`、`指令合集.txt` 等）不属于审查范围，即使对话中修改过，也**一律不审查、不出现在审查结果中**（下方 git 命令本身会排除它们，但基于对话上下文审查时也须遵守）。若本次改动全部属于被忽略文件，直接告知用户"改动均为 Git 忽略文件，不在审查范围内"。不确定某文件是否被忽略时，用 `git check-ignore <路径>` 验证。
1. **按变更复杂度分流**（与 commit-message-generator 的"简单/复杂修改"分流对齐）：
   - **简单变更（快速通道）**：纯样式数值调整（颜色 token、间距、尺寸）、注释、重命名等无逻辑改动的变更，且对话上下文已完整覆盖改动内容与意图（如改动由本轮对话产生）时，跳过步骤 2-5，**不执行任何 git 命令**，直接基于对话上下文审查；维度精简为「项目规范合规」（硬编码颜色/魔法数字）、「无效修改」、关联一致性（跨文件常量、双面板样式是否同步）；对存疑点直接 Read 源文件核实后再下结论
   - **复杂变更（完整流程）**：涉及新逻辑、重构、新增文件、跨模块联动，或对话上下文不足以确信完整覆盖改动时，执行步骤 2-5
2. 执行 `[Console]::OutputEncoding = [Text.Encoding]::UTF8; git -c core.quotepath=false diff HEAD --no-color --output=.git-diff.txt`，将暂存+未暂存的所有变更输出到项目根目录的临时 txt 文件（`--output` 绕过 PowerShell 管道，避免行尾截断与编码损坏，**禁止用 `>` 重定向替代**——PowerShell 会写成 UTF-16；`--no-color` 去除 ANSI 转义码；`-c core.quotepath=false` 防止中文路径被转义成八进制序列——本项目存在大量中文目录与中文文件名；`git diff HEAD` 一条命令同时覆盖暂存与未暂存，不会产生空文件）；用户指定文件则直接读全量
3. 执行 `[Console]::OutputEncoding = [Text.Encoding]::UTF8; git -c core.quotepath=false ls-files --others --exclude-standard` 列出未跟踪的新文件（输出量小，直接读终端输出即可，无需落盘；可与步骤 2 用分号合并为一条命令）——`git diff HEAD` **不含 untracked 文件**，会漏审新建的模块/对话框/服务；对列出的每个文件用 Read 工具读取全量内容一并审查
4. 使用 Read 工具读取 `.git-diff.txt`，获取已跟踪文件的变更；阅读变更区域前后各 20 行上下文，理解改动意图；**报告行号时以 `@@` 段头标注的起始行为基准换算回源文件真实行号**，不要直接使用 diff 内的相对位置；对将写入报告的 🔴/🟡 项，落报告前回读源文件对应区域确认真实行号（`@@` 换算本身易错，行号作为修复依据时尤须确认）
5. 生成审查结果后，删除 `.git-diff.txt`（已在 `.gitignore` 中；若上次审查中断残留，本次开始前先清理）
6. 按下方 7 个维度逐一审查
7. 仅输出有问题项，全通过输出"✅ 未发现问题"

## 审查维度

> 🔴 必须修复 | 🟡 建议优化

### 1. 过度设计 🔴
不必要的抽象层只有一个实现；引入未使用的依赖；为"以后可能用到"写代码或加参数；简单逻辑套复杂模式；为只调用一次且无复用价值的单个条件判断抽取工具函数。

**不算过度设计**：项目既有的合理架构——`_update_styles()` 主题刷新模式、`core/*_service.py` 服务层拆分、`utils/theme_colors.py` 颜色 getter、`dialogs/base_frameless_dialog.py` 等基类设计。

### 2. 冗余代码 🔴
变量赋值未使用；导入未引用；重复代码；dead code；空的 `__init__`/`pass`；注释掉的整块代码（应直接删除）。

⚠️ Qt 事件重写方法（`mousePressEvent`、`dropEvent` 等）由 Qt 事件分发机制自动调用，跨模块经 `self._service` 动态调用的方法 Vulture 也无法识别（白名单见 `pyproject.toml` 的 `[tool.vulture]`），**不算**冗余代码。

### 3. 无效修改 🟡
不影响运行结果的改动；只声明无实现；改了非任务范围文件（除非是顺带修复的明确 bug）；格式与功能变更混杂，应拆分为独立提交。

### 4. 复杂逻辑 🟡
嵌套超 3 层；函数超 50 行；同类分支超 5 个未用查表法；魔法数字未定义为有意义的常量或说明来源；晦涩正则/算法无注释说明意图；行长超 100 字符（《开发规范》§3.1）。

### 5. 过度防御 🟡
`__init__` 中 `hasattr` 守卫 `setup_ui` 后才有的属性；多层 try/except 嵌套可合并；对不可能为 None 的值做 None 检查；对框架保证的属性做防御性检查。

**不算过度防御**（合理的边界防御）：用户输入/文件路径校验、文件 IO 与网络请求的异常处理、调用顺序无法调整时的 `hasattr` 守卫。

### 6. 项目规范合规 🔴

仅检查**本次变更代码**，依据 `文档/开发规范.md`：

| # | 检查项 | 出处 | 违规信号 |
|---|--------|------|---------|
| 1 | 颜色管理 | 《开发规范》§4.5.1 | 硬编码颜色值（`QColor(r,g,b)`、`"#xxx"` 样式），需走 `theme_colors.py` |
| 2 | 异常处理 | 《开发规范》§3.4 | 裸 `except:` 或 `except Exception:`，需指定具体类型 |
| 3 | 日志输出 | 《专项规范/日志系统规范》§7 | 业务代码用 `print()`，需改用 `get_logger()` |
| 4 | 类型注解 | 《开发规范》§3.7 | `typing.List/Dict/Tuple/Optional`，需改 PEP 585 内置泛型 |
| 5 | Nuitka 兼容 | 《开发规范》§3.7.1 | 用了 `list[...]`/`dict[...]` 但无 `from __future__ import annotations` |
| 6 | 资源路径 | 《开发规范》§2.4 | 用 `__file__` 拼资源路径，打包失效，需用 `get_base_path()` |
| 7 | 线程安全 | 《专项规范/图片处理规范》§3 | `QThread.wait()` 阻塞 UI，需用标志位取消 |
| 8 | 主题适配 | 《开发规范》§3.8.3 | 新组件缺 `_update_styles()` + `qconfig.themeChangedFinished` 连接 |
| 9 | 跨面板同步 | 《开发规范》§4.3 | `set_image_data` 等方法缺 `emit_sync` 参数防信号循环 |

> 仅简单类型的文件不需要第 5 项检查。

### 7. 测试完整性 🔴

项目用 pytest + pytest-qt，测试位于 `tests/test_*.py`。审查逻辑层（`core/`、`utils/`）改动时检查：

- 改动了 `core/` 服务或 `utils/` 工具函数的行为，但对应 `tests/test_*.py` 未同步更新，导致测试失败或与实现脱节
- 修改了被测函数的签名或返回值，却未更新断言
- 新增有明确输入输出的纯函数（颜色转换、算法类逻辑），完全无测试覆盖
- 测试中 mock 的模块路径与实际导入路径不一致

> 纯 UI 组件（`ui/`、`dialogs/`）、纯样式改动不强制补测试。

## 输出格式

| # | 文件:行号 | 严重度 | 维度 | 问题描述 |
|---|----------|--------|------|---------|
| 1 | xxx.py:65 | 🔴 | 冗余代码 | 变量 `result` 赋值后未使用 |
| 2 | xxx.py:120 | 🟡 | 复杂逻辑 | 函数 `parse_data` 超 50 行 |
| 3 | xxx.py:45 | 🔴 | 项目规范合规 | 硬编码颜色，应使用 `get_text_color()`（《开发规范》§4.5.1) |

- 每项附 1-2 句修复建议
- 🔴 必须修复项排在前面，🟡 建议优化项排在后面
- 若某维度无问题，不输出该维度
